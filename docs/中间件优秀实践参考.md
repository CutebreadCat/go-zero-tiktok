# 参考项目中间件优秀实践总结

> 汇总 GCFeed(Gin 单体)与 fzuhelper-server(Hertz+Kitex 微服务)的中间件设计精华,标注可借鉴到 go-zero-tiktok 的落地方式。
> 参考只读,不改这两个项目。

---

## 一、鉴权中间件

### 1. 中间件作为"工厂函数 + 依赖注入"(GCFeed)

`NewJWTAuth(jwtManager)` 把 JWT 管理器作为参数传入,而非全局单例 → 便于测试替换(mock)。

```go
// GCFeed: apps/api/internal/interfaces/http/middleware/jwt_auth.go
func NewJWTAuth(jwtManager infra.JWTManager) app.HandlerFunc {
    return func(c *gin.Context) {
        // 只做三件事:解析 Bearer → 校验 → 注入 context
    }
}
```

**优秀点**:中间件只做"解析 + 校验 + 注入 context",业务取值逻辑收敛到 handler 侧工具函数,中间件不碰业务。注入用**包级常量键**(`ContextUserIDKey`),避免 handler 硬编码字符串。

**go-zero 借鉴**:go-zero 的 rest 中间件天然是 `func(next http.HandlerFunc) http.HandlerFunc`,可按路由 `server.AddRoutes(rest.WithMiddlewares(...))` 注入;JWT 校验器可设计为工厂函数复用。

### 2. 可选鉴权 vs 强制鉴权分离(GCFeed)

`NewOptionalJWTAuth`(匿名可访问,有 token 则个性化)与 `NewJWTAuth`(强制)是**两个独立中间件**,而非一个布尔开关。

```go
// 可选鉴权:无 token / 坏 token 都放行,只有解析成功才注入
func NewOptionalJWTAuth(jwtManager) app.HandlerFunc {
    return func(c *gin.Context) {
        header := c.GetHeader("Authorization")
        if header == "" { c.Next(); return }
        claims, err := jwtManager.ParseAndValidateToken(...)
        if err != nil { c.Next(); return }  // 坏 token 也放行
        c.Set(ContextUserIDKey, claims.UserID)  // 成功才注入
        c.Next()
    }
}
```

**优秀点**:handler 侧用 `exists` 判断区分"未登录"和"登录 ID 异常",而不是只判 `userID > 0`。

**go-zero 借鉴**:Feed 个性化场景可加"可选鉴权"中间件(匿名能看 Feed,登录用户个性化)。

### 3. 内部 token 用 `subtle.ConstantTimeCompare`(GCFeed)

保护 `/internal` 接口,防时序侧信道攻击:

```go
if subtle.ConstantTimeCompare([]byte(provided), []byte(token)) != 1 {
    c.AbortWithStatusJSON(http.StatusUnauthorized, ...)
}
```

**优秀点**:不用 `==`(存在时序侧信道),token 在工厂创建时 `TrimSpace` 一次闭包捕获。

**go-zero 借鉴**:若将来有内部服务接口,用常量时间比较 + 独立 `X-Internal-Token` 头,与用户 JWT 隔离。

### 4. 非对称签名 + 防算法混淆 + 两段式解析(fzuhelper-server)

`api/mw/token.go` 用 **Ed25519 非对称签名 JWT**:
- 私钥服务端签发,公钥硬编码下发校验;
- keyfunc 中**显式断言签名算法**(`token.Method.(*jwt.SigningMethodEd25519)`),防 JWT 算法混淆攻击;
- **两段式解析**:先 `ParseUnverified` 只解 claims 拿 `Type`,再 `ParseWithClaims` 真正校验签名;
- 错误按类型细分(访问过期/刷新过期),客户端可差异化引导续期。

**优秀点**:密码学选型有意识权衡(注释写明 Ed25519 兼顾安全与性能),算法固定防混淆,过期错误可诊断。

**go-zero 借鉴**:当前 go-zero-tiktok 用 HS256 对称签名,可评估升级 Ed25519;至少应固定算法校验。

### 5. 滑动续期(fzuhelper-server)

`Auth()` 在校验通过后**重新签发一对新 token** 经响应头返回(`Access-Token`/`Refresh-Token`),每次受保护请求自动延长会话,客户端无需主动调刷新接口。

**go-zero 借鉴**:可评估是否需要;滑动续期会增大签发频率,需权衡。

## 二、跨服务登录态透传——metainfo + TTHeader(fzuhelper-server ⭐架构亮点)

网关把登录态注入 **metainfo**(而非普通 context),跨 RPC 自动透传:

```go
// 网关中间件注入
metainfoContext.WithLoginData(ctx, &model.LoginData{...})  // 用 WithPersistentValue + sonic 序列化
// 微服务 handler 读取
metainfoContext.GetLoginData(ctx)  // 一次注入,整条链路可见
```

配套:服务端/客户端都配 `transmeta.ServerTTHeaderHandler` / `ClientTTHeaderHandler` + `WithPersistentValue`,打通 TTHeader 协议。

**优秀点**:登录态一次注入、跨 RPC 零手写透传字段,降低多服务上下文维护成本。微服务侧**零鉴权**(信任内网),全部鉴权收敛在网关 —— 经典"边缘鉴权"模型。

**go-zero 借鉴**:go-zero 的 zrpc 用 `metadata` / `metadata.OutgoingContext` 透传。当前 go-zero-tiktok 各服务只接收网关传入的 `user_id`,可考虑统一透传一个 `LoginData` 结构,避免每个 RPC 手写 `user_id` 参数。

## 三、可观测性中间件

### 1. 指标中间件用"路由模板"规避高基数(GCFeed ⭐)

```go
route := c.FullPath()          // 稳定路由模板,如 /videos/:videoId
if route == "" { route = c.Request.URL.Path }
HTTPRequestsTotal.WithLabelValues(method, route, status).Inc()
```

**优秀点**:用 `c.FullPath()` 而非 `c.Request.URL.Path`,避免 `/videos/123` 和 `/videos/456` 拆成不同 label 导致**指标高基数爆炸**——这是监控经典陷阱。

**go-zero 借鉴**:go-zero 的 `httpx`/metrics 中间件采集时,路由标签应取**路由模板**而非原始 URL Path。

### 2. 全局中间件三件套:链路追踪 → 恢复 → 限流(fzuhelper-server)

```go
h.Use(hertztracing.ServerMiddleware(traceCfg))  // OTel 链路
h.Use(recovery.Recovery(recovery.WithRecoveryHandler(recoveryHandler)))  // 自定义恢复
h.Use(adapter.SentinelServerMiddleware(...))    // 限流
```

- **Recovery**:自定义 handler 记录完整堆栈到 logger,返回统一 JSON 业务错误码(而非裸 500 / 泄漏堆栈);
- **限流**:全局 QPS 5000 + 精确接口 QPS 100(允许排队 2s),被限流**返回业务码而非裸 429**(对客户端解析更友好)。

**go-zero 借鉴**:go-zero 已有内置 recovery;可加 OTel 链路中间件;限流可用 `core/limit` 或接入 Sentinel,按"全局 + 关键接口"两级配置。

## 四、装配与横切面

### 1. 按路由粒度挂装,白名单式默认(fzuhelper-server)

Hertz 生成器留 `middleware.go` 手写层,每个路由节点对应 `_xxxMw()`;**默认为空(公开)、按需追加鉴权**,天然实现白名单式路由控制。敏感分组挂 `Auth()+GetHeaderParams()`,公开接口返回 nil。

**go-zero 借鉴**:当前 go-zero-tiktok 用全局 `token.WithAuth` + `publicPaths` 白名单(已实现)。可保持,注意公开/私有分组清晰。

### 2. 统一错误码 + 统一响应(fzuhelper-server)

中间件与微服务共用同一套 `pkg/errno`(语义化错误码)+ `pack.RespError`/`BuildBaseResp`(统一错误→响应映射),保证全链路错误格式一致。

**go-zero 借鉴**:go-zero-tiktok 已有 `pkg/xerr`,保持中间件/逻辑统一用 `xerr`,不裸返 HTTP 状态码。

## 五、对 go-zero-tiktok 的落地优先级建议

| 优先级 | 借鉴点 | 出处 | go-zero 落地方式 |
|---|---|---|---|
| P0 | 指标中间件用路由模板标签 | GCFeed | 网关 metrics 中间件取路由模板规避高基数 |
| P0 | 统一错误码/响应(已有 xerr) | fzuhelper | 维持,中间件统一走 xerr |
| P1 | 可选鉴权(Feed 匿名可看) | GCFeed | 新增 optional 鉴权中间件 |
| P1 | 跨服务登录态透传 LoginData | fzuhelper | go-zero metadata 透传,替代手写 user_id 参数 |
| P1 | Recovery 自定义 + OTel 链路 | fzuhelper | go-zero 内置 recovery + otel 中间件 |
| P2 | 内部 token 常量时间比较 | GCFeed | 内部接口鉴权 |
| P2 | 非对称签名 + 防算法混淆 | fzuhelper | 评估 JWT 升级 Ed25519 |
| P2 | 分接口限流(业务码) | fzuhelper | core/limit 两级配置 |

---

## 关键结论

- **GCFeed 强在**:鉴权中间件职责单一、可选鉴权分离、内部 token 安全比较、指标高基数规避。
- **fzuhelper-server 强在**:Ed25519 密码学选型、metainfo+TTHeader 跨服务透传、全局中间件三件套、分接口限流、统一错误码。
- **对 go-zero-tiktok**:当前鉴权/白名单已基本到位,最值得先借鉴的是**指标路由模板标签**和**跨服务登录态透传**两项。
